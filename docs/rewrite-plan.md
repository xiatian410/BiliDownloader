# BiliDownloader 重写：Issue 核查与多端改版方案

核查日期：2026-10-28（北京时间）。代码基线：`flutter/migration` / `91d5ff4`。

本文保留重构前的审计快照与验收目标，下文“当前实现”“尚未实现”均针对上述基线。后续已完成的实现、测试和剩余工作见 [重构实施状态](rewrite-progress.md)。

本轮交付问题清单与实施方案。以下改进尚未实现；生产代码没有修改。上游 Issue 是需求和复现线索，不能直接当作 Flutter 版的缺陷结论。

## 核查范围与结论

读取了 [上游 Issues](https://github.com/Majjcom/BiliDownloader/issues) 的 9 个未关闭问题、33 个已关闭问题，以及相关讨论；对照 Flutter 的输入解析、接口映射、下载、存储和界面调用链。

建议把项目发展为以任务管理为中心的跨平台下载器。保留已经验证的下载能力，重新设计页面和交互，不再要求模仿 Python/PySide 的四标签、四步向导或原有样式。

最先处理的是输入不丢失、文件不冲突、画质信息明确和小屏大字体可用，然后完成自适应界面、批量操作与可恢复的任务管理，再增加字幕和媒体库附件。UP 主主页、收藏夹、命令行和完整 Web 下载应在这些基础稳定后接入。

## 已关闭问题中仍值得借鉴的内容

- [#42 4K 实际下载成 480P](https://github.com/Majjcom/BiliDownloader/issues/42)：维护者指出登录/会员限制。它不是承诺通过客户端修复就能取得高画质的问题。我们应展示“接口声明的格式”和“当前实际可下载的流”的区别，并明确降级策略。
- [#31 HTTP 412](https://github.com/Majjcom/BiliDownloader/issues/31)：该旧问题的讨论指向封面访问，不能把所有 412 都归为播放接口失败。当前 Flutter 封面预览与保存采用不同请求头，值得统一和验证。
- [#36 下载停止](https://github.com/Majjcom/BiliDownloader/issues/36)、[#40 重试后进度闪烁](https://github.com/Majjcom/BiliDownloader/issues/40)：后者有明确 1.4.0 修复记录。我们的队列已按任务状态调度，应保留“旧请求结束后才能恢复同一任务”的回归测试。
- [#37 文件被覆盖](https://github.com/Majjcom/BiliDownloader/issues/37)、[#22 标题截断](https://github.com/Majjcom/BiliDownloader/issues/22)：当前存在文件时会拒绝覆盖，但标题截断仍会使不同视频竞争相同路径。避免数据覆盖与保证所有任务都能正确命名，是两件事。
- [#32 无音频流报错](https://github.com/Majjcom/BiliDownloader/issues/32)：当前 `audio == null` 可映射为空列表；普通视频可以没有音轨，只有“仅音频”任务应提示无音轨。
- [#39 登录后卡死](https://github.com/Majjcom/BiliDownloader/issues/39) 的旧版讨论指向接口变化；本项目此前修复的是 Linux 系统密钥环阻塞，不能把两者当成同一根因。
- [#16 合并卡住](https://github.com/Majjcom/BiliDownloader/issues/16) 因缺少复现信息关闭，不是已证实修复。当前 FFmpeg 调用没有任务级取消/超时兜底，属于应补的控制能力，尚未复现真实 FFmpeg 挂起。
- [#18 任务栏启动异常](https://github.com/Majjcom/BiliDownloader/issues/18) 与工作目录相关；原生发布包应补“从不同工作目录启动”的回归验证。

## 本轮实测与源码证据

### 1. 多 BV 输入丢失：已复现

输入 `BV1gx4y187fX;BV1Bf421B7XS;BV176421Z7qt`，实际返回 `BV1gx4y187fX`。

来源：`flutter_app/lib/core/models.dart:17`；控制器 `resolve` 只接收一个 `VideoId`，不能只把正则改成 `allMatches` 就算完成批量功能。

### 2. 小屏大字体溢出：已复现

组件探针加载项目的 `HarmonyOS Sans SC` 字体后，在 2 倍系统字体下测试输入页及设置页：

| 逻辑宽度 | 结果 |
| --- | --- |
| 320px | 输入页出现约 9.3px 横向 RenderFlex 溢出 |
| 360px | 输入页与设置页通过 |
| 760px | 输入页与设置页通过 |

来源：`flutter_app/lib/app.dart:143` 的标题栏 Row；品牌文本没有可收缩约束。这里是字体缩放测试，不是 Windows 125%/150%/200% 显示缩放实机验证。不能用禁止字体缩放来消除错误。

### 3. 长标题发生路径冲突：已复现字符串碰撞

两个标题的前 80 个字符相同、后缀不同，`safeFilename` 返回相同结果；当分集号和分集名称也相同时，最终目标路径会相同。

来源：`flutter_app/lib/core/models.dart:272`、`flutter_app/lib/platform/download_native.dart:173`。当前存在文件检查会拒绝第二个写入，不能将本轮结果描述为已复现“覆盖丢数据”。建议在安全截断后保留 BV/EP/CID 或稳定短标识，并显示文件名预览。

### 4. 画质说明不足：已复现选择行为

构造接口格式含 4K/480P、实际 DASH 仅有 480P 的数据：界面数据仍列出 4K，`selectVideo(120, 7)` 返回质量 ID 32。当前代码将清晰度定义为上限，这个回退符合原有实现；问题在于新界面需要让用户理解实际结果。

来源：`flutter_app/lib/core/models.dart:203`、`flutter_app/lib/app.dart:530`。任务卡目前直接显示实际质量编号，应转换为可读名称，并标注“期望 / 实际”。限制原因仅在接口提供足够证据时解释，不能凭空认定是会员或风控。

### 5. 停流下载是否无限卡住：针对性测试通过

本地 HTTP 服务在返回部分正文后停止发送，测试将接收超时缩短至 150ms、重试间隔设为 0。实际触发 3 次正文请求后以 `receiveTimeout` 结束；没有无限重试。生产设置仍是 20 秒分块接收超时与既有有限重试，未改动。

来源：`flutter_app/lib/platform/download_native.dart:72`。这个结果只覆盖“连接未断但不再发送正文”，不等同于解决真实 B站卡住、磁盘错误、FFmpeg 挂起或系统文件导出失败。

### 6. 待验证的源码风险

- 封面：`app.dart:353` 的 `Image.network` 没有配置 B站请求头；`app.dart:376` 的保存操作配置了 `biliHeaders`。统一封面获取服务后，用带请求头要求的本地服务和真实 CDN 验证；封面失败不应阻断视频信息。
- 登录状态：`app_controller.dart:92` 只检查 Cookie 非空，不能证明服务端会话有效。应区分未登录、校验中、已登录、已过期；无需增加周期性轮询。
- 合并控制：`download_native.dart:18` 等待 FFmpeg 返回，当前没有任务级取消或明确的停滞诊断；需要基于真实执行事件设计，而非任意固定延时后强制失败。
- 跨重启：队列、部分文件身份和历史在内存中；进程退出后的恢复尚未实现。

审计探针与日志保留在本地 `artifacts/issue-audit/`，未加入正常测试套件。布局探针保留失败结果作为后续修复用例；停流探针通过。不能把本轮描述为“所有新增检查都通过”。

其中“内容预览”指提交前显示将下载视频、音频、字幕等哪些内容，不等同于增加在线播放器。

值得转化为验收要求的源码细节：

1. **分项任务状态。** lanyeeee 的 [任务组件](https://github.com/lanyeeee/bilibili-video-downloader/blob/1254c6bf2a09a590163091e67651bfc9942171e2/src/panes/DownloadPane/components/DownloadProgress.vue) 展示选中的内容；[任务管理器](https://github.com/lanyeeee/bilibili-video-downloader/blob/1254c6bf2a09a590163091e67651bfc9942171e2/src-tauri/src/downloader/download_manager.rs) 区分任务并发与媒体分块并发。我们应先让下载、合并、导出及附件的结果可见，再评估分块加速；现阶段不增加新的轮询或重试。
2. **筛选后的批量操作范围。** Bili23 的 [列表代理模型](https://github.com/ScottSloan/Bili23-Downloader/blob/50594cd1f8ef7fe6845826f2642c3ef90fcee804/src/gui/component/download_list/proxy_model.py) 在筛选生效时仅作用于可见任务。我们的按钮应显示明确数量，例如“暂停选中的 5 项”，不影响被筛掉的任务。
3. **任务入队时冻结设置。** Bili23 的 [命名快照测试](https://github.com/ScottSloan/Bili23-Downloader/blob/50594cd1f8ef7fe6845826f2642c3ef90fcee804/test/test_task_naming_snapshot.py) 覆盖后续命名选择不改变排队任务。我们创建任务时保存目标目录、命名模板及下载选项，设置页修改只影响之后创建的任务。
4. **完成记录与恢复。** Bili23 的 [数据库实现](https://github.com/ScottSloan/Bili23-Downloader/blob/50594cd1f8ef7fe6845826f2642c3ef90fcee804/src/util/download/task/db.py) 用事务迁移任务状态；[完成落盘测试](https://github.com/ScottSloan/Bili23-Downloader/blob/50594cd1f8ef7fe6845826f2642c3ef90fcee804/test/test_task_completion_durability.py) 针对完成通知与持久化之间的窗口。我们的验收也要覆盖成品已生成、记录尚未完成时中断进程，并在恢复时核对文件与记录。
5. **稳定的媒体身份。** Bili23 的 [标识计算](https://github.com/ScottSloan/Bili23-Downloader/blob/50594cd1f8ef7fe6845826f2642c3ef90fcee804/src/util/download/task/hash_id.py) 让解析端与入库端共用媒体标识。我们应按媒体/分集标识提示“已下载”，同时比较任务类型和输出选项；同一视频的音频任务或不同画质不能一律当作重复并静默跳过。

两者都提供字幕和媒体库附件的参考。建议增加 CC 字幕及语言选择，优先支持 SRT；章节与容器内嵌放在后续增强阶段。功能入口采用常用预设加高级选项，避免让新建任务页变成密集的复选框面板。首版重点是下载流程、队列恢复和多端体验。

## 新界面方向

### 信息架构

采用三个主要入口：**新建下载、下载任务、设置**。已完成/失败/暂停作为任务筛选；账户状态放在应用导航区域，关于与诊断放入设置。

核心流程改为：

**粘贴一个或多个链接 → 解析结果与分集选择 → 确认下载类型/画质/保存位置 → 加入任务队列。**

解析预览和下载配置在宽屏可同时展示；手机按内容分组展开。减少反复翻页，但保留提交前预览与明确的批量确认。

### 各端布局

| 场景 | 布局与操作 |
| --- | --- |
| 桌面宽屏 | 左侧导航、中央任务列表、可展开的右侧详情；支持窗口拉伸、键盘导航、批量选择和快捷粘贴 |
| 平板/窄桌面 | 收起为导航栏，保留主列表；详情使用抽屉或独立页，避免把三列硬挤到一起 |
| Android/手机宽度 | 底部导航、单列任务卡、底部弹出详情；主要操作保持约 48dp 触控区域，处理软键盘与系统安全区 |
| Web | 复用布局和状态模型；后端未接入时明确为预览，文件与会话能力由平台适配层提供 |

视觉采用现代 Material 3 的组件与状态反馈：浅灰白背景、克制的莓粉强调色、清楚的文字层级、适度圆角和间距；深浅主题跟随系统。状态同时使用图标与文字，不能只靠颜色区分。桌面信息密度与手机触控尺寸分别调整。

### 新建下载页

- 多行输入，显示识别数量、重复项和无效项；保留原始输入，数量超限时明确提示，不静默截断。
- 每个来源单独显示标题、封面、分集与解析结果；部分失败不会丢掉已成功项。合集按来源/章节/分集展开，支持搜索、全选及明确的选择数量。
- 视频/仅音频/仅弹幕为明确的任务类型，相关选项随类型变化。
- 提交区域汇总实际下载内容；字幕加入后可选择语言。历史中的相同媒体提供“查看记录 / 跳过 / 再次下载”，由用户决定。
- 画质显示当前可用流与实际结果；必要时给出用户可选择的回退策略。
- 输出目录、文件名和伴随文件在提交前可预览。Android 显示易读的系统目录名称，不直接把 `content://` 当作主要界面文字。

### 下载任务页

- 任务卡显示标题/分集、实际质量、已下载大小、速度、阶段和可用操作。
- 分开呈现“解析、下载视频、下载音频、合并、导出”，避免一个到达 100% 的进度条长期停留却没有说明。
- 暂停/继续/取消与任务状态一致；批量操作只作用于当前选择范围内且允许该操作的任务。筛选时显示作用数量，隐藏项不受影响。
- 支持标题、UP 主、BV 号搜索及状态/类型筛选；完成项可打开文件、查看保存位置、再次下载。手机提供显式按钮，不把右键菜单作为唯一入口。
- 封面、字幕等附件各自显示成功/失败；可重做失败项，避免因附件失败重新下载已经完成的视频。
- 错误详情按接口拒绝、会话失效、缺少流、网络超时、磁盘/权限、合并和导出分类。日志去除 Cookie、签名链接等敏感内容。
- 长列表采用按需构建；分集选择也应避免一次创建数百个复杂组件。

### 设置页

分组为账户、下载、保存规则、外观、诊断。提供并发上限、默认下载类型、目录规则、命名模板、主题和语言；关于信息放在次级区域。

## 实施顺序与验收

现有代码已有 `core/` 与 `platform/` 分层，可继续利用。`app.dart` 中的封面下载、文件导出等操作应移到服务层；界面使用业务状态，不直接拥有下载执行。先明确队列与平台接口，再逐页替换，避免为了换皮引入新的轮询或重复请求。

## Web 的可行范围与下一步验证

此前的 [构建与验证记录](flutter-validation.md) 已确认 Flutter Web 能编译并在 Chrome 桌面和手机宽度渲染；纯静态预览尚不能完成登录与下载。真实浏览器访问视频信息、nav、二维码接口被 CORS 拒绝；原生请求还遇到过 HTTP 412。这是两类不同的限制，代理请求只改变跨域访问方式，不能保证上游接口不拒绝请求。

[Flutter 官方说明](https://docs.flutter.dev/platform-integration/web/web-images) 也指出浏览器跨域资源读取受服务器 CORS 配置约束。参考项目使用 Web 前端或跨平台 GUI，不构成纯浏览器下载可行的证明。

建议完整 Web 采用 **Flutter Web 界面 + 本机或 NAS 下载服务**：浏览器提交任务、查看状态和取回成品；服务负责会话、B站请求、文件及 FFmpeg。远程服务器部署可以作为后续选择。单纯加入浏览器版 FFmpeg 仍不能解决接口和会话访问限制。

正式实现前先做一个纵向验证：在正常 Chrome 安全设置下，完成登录、解析一个有权访问的视频、下载合并、取回文件，再验证取消、失败和重新连接的状态。后端必须能报告上游拒绝原因。这个完整链路目前尚未实现或实测通过，不能与“Web 编译通过”混为一谈。
